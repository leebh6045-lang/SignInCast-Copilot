# ADR-001：独立 Agent 服务，不在 Java 工程内

- 状态：已接受
- 日期：2026-11-17
- 决策人：项目作者

## 背景

SignInCast 是已上线的 Spring Boot 单体应用（Java 21，部署在 2 核 1.7G 服务器）。我们要加一层 Agent 能力：模型调用、工具编排、检索、评测。放在哪里？

## 决策

**新建独立的 Python 服务，通过 HTTPS + JWT 调用 SignInCast 的 REST 接口**；Java 工程零改动或极小改动。

## 理由

1. **技术栈隔离**：模型 SDK、向量库、评测脚本都是 Python 生态；混进 Maven 工程会让构建、依赖、部署都变复杂。
2. **迭代风险隔离**：Agent 代码要频繁试错，不能碰已上线的签到主流程。
3. **企业真实形态**：AI 服务与业务系统解耦、通过 API 集成，是大多数企业落地 Agent 的方式。
4. **可演示与可迁移**：独立仓库一个 `docker compose up` 就能起；换一个业务系统（如报销审核）只需换工具层。
5. **面试可讲**：为什么独立服务、为什么通过 API 集成、权限怎么隔离，都是能展开的设计取舍。

## 后果

正面：
- 原系统稳定性不受影响
- 可单独部署、单独评测、单独升级
- 工具层可以直接映射真实接口

负面：
- 多一个服务要部署与监控
- 需要维护服务账号与鉴权
- 跨系统调用增加延迟（可接受，单次查询在百毫秒级）

## 替代方案

| 方案 | 为何不选 |
| --- | --- |
| monorepo（Java 工程里放 `copilot/`） | 构建与部署耦合；面试叙事弱；风险传染 |
| Java 内嵌 Agent 模块（Spring AI） | 依赖生态弱、评测工具少；模型试错成本高 |
| 纯本地脚本（不服务化） | 无法演示 HTTP/HITL 全链路，也无法部署 |

## 后续

- M1 落地服务账号与 JWT 刷新
- M2 评估是否需要只读 `SERVICE` 角色（Java 侧约 1 天工作量）
