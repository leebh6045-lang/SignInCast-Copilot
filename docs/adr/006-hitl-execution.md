# ADR-006：HITL 持久化与执行器（模型提议、人确认、服务端执行）

- 状态：已接受
- 日期：2026-11-17

## 背景

M1 的 HITL 只做到"提议"：动作存在内存、写操作没有真实执行。M2 要补齐三件事：
1. 待确认动作与审计要跨重启保存（不能进程一退就丢）
2. 确认后要真的调用 SignInCast 写接口
3. 模型仍然不能自确认、不能自执行

## 决策

1. **持久化**：待确认动作与审计写入 SQLite（`data/copilot.db`），使用版本化迁移（`schema_migrations`，只追加不修改）。
2. **存储抽象**：`PendingActionStore` 协议 + 两个实现（内存用于单测、SQLite 用于运行）。
3. **确认与执行分离**：
   - `POST /api/actions/{id}/confirm`：校验令牌、置为 `confirmed`
   - `POST /api/actions/{id}/execute`：`ActionExecutor` 校验令牌 → 调 `SignInCastWriter` → 成功置 `executed` 并落库
4. **令牌只走人工通道**：`propose_*` 工具不返回 `confirm_token`（有专门测试），CLI/API 才拿得到。
5. **幂等**：动作级幂等键（任务 + 学生集合）避免重复提议；执行级幂等（已执行动作返回首次结果，`replayed: true`）；服务端写接口本身是 upsert，逐学生重试安全。
6. **部分失败**：多学生动作逐个执行，结果区分 `succeeded/failed`；有失败时动作保持 `confirmed`（可重试），审计写 `execute_partial`。
7. **mock 模式禁止写**：回放数据不含写接口响应，`SignInCastWriter` 直接返回 `CONFIG_ERROR`，避免"假装成功"。

## 理由

- 跨重启不丢，才能对"谁在什么时候补签了谁"负责
- 提议/确认/执行三段分离，是 Agent 安全边界的最小可用形态
- 服务端 upsert 语义让"重试"不会产生重复记录，这是能自动/手动重试的前提
- mock 模式明确拒绝写，比静默失败或伪造成功更可信

## 后果

正面：
- 审计可查、动作可恢复、失败可重试
- 模型无法自导自演"提议→确认→执行"
- 多学生批量操作有明确的部分失败语义

负面：
- 多学生动作非原子（不是事务），中途失败会留下部分已写记录；靠逐学生幂等 + 重试收敛（已在 limitations 记录）
- SQLite 单进程写入，服务多实例部署时需要换成集中存储（M3 以后）

## 替代方案

| 方案 | 为何不选 |
| --- | --- |
| 动作只存内存 | 重启即丢，审计无法追溯 |
| 模型直接调写接口 | 幻觉即事故 |
| 确认与执行合并成一个接口 | 无法人工复核影响范围，也丢审计点 |
| 写操作自动重试 | 多学生场景难判断部分成功，风险高 |
